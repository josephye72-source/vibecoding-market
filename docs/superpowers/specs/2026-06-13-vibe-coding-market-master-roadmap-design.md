# Vibe Coding Market 大蓝图与版本路线图

日期：2026-06-13
状态：草案，等待用户审阅

## 1. 终极目标

Vibe Coding Market 的终极目标是成为一个公开、公益、可复现的 vibe coding 项目地图。

它帮助普通人通过一组高完成度的 Web 项目理解：

- AI 不只是聊天工具，也可以陪人把想法做成可运行的软件；
- 编程小白不需要先学完整套前端课程，也可以从一个具体项目开始；
- 一个项目不只是最终代码，还包括想法、Prompt、Codex 操作过程、调试过程、二创路径；
- 好的 vibe coding 不是随便让 AI 生成代码，而是把想法拆清楚、把反馈说清楚、把结果持续打磨。

长期来看，这个站点要沉淀的是一套公开的实践方法：

想法 -> 项目选择 -> 在线体验 -> 复杂度拆解 -> Codex 复现 -> 源码阅读 -> 二创发布。

站点本身可以越来越完整，但它不应该变成商业课程、训练营、社区平台或 SaaS 工具。它的核心身份始终是：一个高质量、开源、可学习、可复现的项目集合。

## 2. 北极星

项目的北极星不是访问量，也不是项目数量，而是：

一个完全小白能不能通过这里的项目，用 Codex 做出自己的第一个可发布 Web 作品。

所有版本规划都应该围绕这个问题展开：

- 用户是否愿意点开项目？
- 项目是否足够好看、好玩、有用？
- 文档是否能让小白复现？
- 源码是否足够清楚？
- 用户是否有动力二创并公开分享？
- 这个过程是否能体现 vibe coding 的真实价值？

如果某个功能不能增强这条路径，就不应该优先做。

## 3. 长期产品形态

Vibe Coding Market 最终可以由四层组成。

第一层是项目画廊。用户可以看到不同难度、不同类型、不同视觉风格的 Web 项目，并在线体验。

第二层是复现系统。每个项目都有源码、Prompt、Codex 操作步骤、常见问题和二创任务，让用户可以从空文件夹开始做出来。

第三层是项目路径。项目不只是散落的 demo，而是按能力、难度和兴趣组织成路径，比如纯 Web 入门、小游戏、生活工具、数据可视化、轻量创意工具等。

第四层是公开迭代。用户可以通过 GitHub、社交媒体或反馈入口贡献建议、展示二创结果、提出新项目想法。这里可以有社区信号，但不急着做社区产品。

长期形态可以更丰富，但底层原则不变：先体验，再复现，再二创。

## 4. 版本路线总览

| 版本 | 阶段目标 | 核心问题 | 产品形态 |
| --- | --- | --- | --- |
| 1.0 | 验证路径 | 小白是否能通过 5 个项目理解并复现 vibe coding？ | 静态项目站 + 5 个完整项目 |
| 2.0 | 扩展结构 | 项目数量增加后，用户是否还能找到适合自己的路径？ | 项目路径化 + 分类筛选 + 更完整文档体系 |
| 3.0 | 形成生态 | 用户是否愿意二创、反馈、贡献项目，并让站点持续生长？ | 开放项目地图 + 贡献机制 + 公开迭代体系 |

## 5. 1.0：路径验证版

1.0 的目标是证明这个想法成立。

这一版不追求规模，只追求闭环。用户应该能完整经历一次：看到项目、玩项目、看源码、跟 Codex 做、产生二创想法。

1.0 包含：

- 首页；
- 5 个纯 Web 项目；
- 每个项目一个在线 demo；
- 每个项目一个源码入口；
- 每个项目一份 Codex 从 0 到 1 操作文档；
- 统一的项目详情页结构；
- 统一的复杂度拆解；
- 一个反馈或社交分享入口。

1.0 推荐项目：

1. 专注番茄钟；
2. 记忆翻牌小游戏；
3. 极简记账本；
4. 习惯打卡日历；
5. 预算 / 分摊计算器。

1.0 的重点不是“做很多”，而是把每个项目做完整。完整的意思是：能玩、好看、源码清楚、文档能跟做、有二创方向。

1.0 不做：

- 登录；
- 后端；
- 数据库；
- 项目投稿；
- 评论区；
- 排行榜；
- 课程系统；
- 多路径推荐；
- AI API 项目；
- 社区平台。

1.0 成功标准：

- 用户能在首页理解这个站点；
- 用户愿意点开至少一个项目；
- 至少一个项目能被小白复现出 70% 以上效果；
- 社交媒体反馈能告诉我们哪个项目最吸引人；
- 我们能总结出一套项目页和 Codex 文档模板。

## 6. 2.0：路径扩展版

2.0 的目标是从“5 个完整项目”扩展到“有组织的项目路径”。

如果 1.0 验证了路径，2.0 就要解决下一个问题：当项目变多时，用户如何选择适合自己的项目？

2.0 可以增加：

- 更多纯 Web 项目，数量可以扩展到 12-20 个；
- 项目分类，比如实用工具、小游戏、创意交互、数据展示、个人效率；
- 难度层级，比如 1 星、2 星、3 星；
- 能力标签，比如表单、状态、列表、localStorage、日期、动画、Canvas；
- 推荐路径，比如“小白第一周”、“先做 3 个工具”、“先做 3 个游戏”；
- 更统一的项目元数据；
- 更清晰的源码阅读导览；
- 更完整的 Prompt 模板库；
- 项目二创案例展示。

2.0 的游戏规划可以扩展成一个小游戏路径：

1. 记忆翻牌；
2. 反应速度挑战；
3. 小型迷宫冒险；
4. 打字防线游戏。

小游戏路径仍然要控制复杂度。每个游戏都应该是单页面、纯 Web、规则简单、能快速反馈。不要过早进入物理引擎、多人游戏、排行榜、关卡编辑器或复杂素材系统。

2.0 可以开始考虑轻量筛选，但不应该做复杂搜索系统。用户只需要能按难度、类型、能力标签找到项目。

2.0 成功标准：

- 用户能根据兴趣或能力找到项目；
- 项目路径比项目数量更有价值；
- 新项目可以复用 1.0 沉淀的文档模板；
- 至少出现一些用户二创反馈；
- 我们能判断哪些项目类型最适合继续扩展。

## 7. 3.0：开放生态版

3.0 的目标是让 Vibe Coding Market 不只是我们自己维护的项目集合，而是一个可持续生长的公开项目地图。

这里的“生态”不是重社区，也不是平台化运营，而是让更多人可以围绕项目贡献、二创、反馈和展示。

3.0 可以增加：

- 项目贡献指南；
- 项目提案模板；
- Codex 过程记录模板；
- 二创作品展示；
- GitHub issue / discussion 作为轻量反馈入口；
- 精选用户复现案例；
- 项目版本历史；
- 项目质量标准；
- 贡献者署名；
- 按主题组织的项目地图。

3.0 可以考虑更高级的项目类型，但仍然要分层：

- 纯 Web 项目仍然是核心；
- 可选 API 项目必须明确标注依赖和风险；
- AI API 项目可以作为高级路径，不进入小白默认路径；
- 需要后端或数据库的项目只能放在进阶区；
- 任何涉及账号、支付、用户数据、上传、公开发布的项目都要谨慎处理。

3.0 的游戏方向可以扩展成更完整的 “Web Mini Games” 分区：

- 入门游戏：翻牌、反应、迷宫；
- 中级游戏：打字防线、轻量平台跳跃、节奏点击；
- 创意游戏：互动故事、分支选择、谜题生成；
- 高级游戏：Canvas 小游戏、关卡数据、简单编辑器。

但游戏分区仍然不应该变成独立游戏平台。它服务的是 vibe coding 学习，而不是游戏发行。

3.0 成功标准：

- 有外部用户提交项目想法或二创案例；
- 有一套清楚的贡献规范；
- 项目质量不会因为开放贡献而下降；
- 用户能看到从入门到进阶的路径；
- Vibe Coding Market 成为一个可被引用、可被学习、可被扩展的公开资源。

## 8. 版本之间的关键转折

从 1.0 到 2.0 的关键转折是：从单条路径变成多条路径。

1.0 只需要证明一个小白可以走完第一条路径。2.0 要解决项目变多之后的组织问题。

从 2.0 到 3.0 的关键转折是：从我们策展变成开放贡献。

2.0 仍然主要由我们设计和维护。3.0 开始接纳外部项目想法、二创案例和贡献，但必须有质量标准。

不要提前把 3.0 的复杂度放进 1.0。尤其不要在 1.0 做账号、投稿、社区、评论、排行榜、复杂搜索。这些会让项目过早变重。

## 9. 内容扩展原则

新增项目必须通过四个问题：

1. 它是否适合在线体验？
2. 它是否能被小白通过 Codex 复现？
3. 它是否有足够吸引人的成品感？
4. 它是否能教一个明确的 Web 能力？

如果一个项目只是实用但不好玩，可能不适合。

如果一个项目好玩但隐藏复杂度太高，也不适合放入小白路径。

如果一个项目只能依赖后端、账号、API key 或复杂服务，应该放到进阶阶段。

如果一个项目只是为了展示技术，而用户没有玩的欲望，也不适合。

## 10. 长期非目标

Vibe Coding Market 长期也不应该变成：

- 训练营；
- 课程售卖站；
- 代码题库；
- 外包项目市场；
- AI 工具导航；
- SaaS 产品；
- 重社区；
- 低质量 demo 集合；
- 只展示结果、不展示过程的作品集。

它可以有课程感，但不是课程平台。

它可以有社区反馈，但不是社区平台。

它可以有项目展示，但不是作品集平台。

它可以有 AI 项目，但不把 AI API 当成默认路径。
