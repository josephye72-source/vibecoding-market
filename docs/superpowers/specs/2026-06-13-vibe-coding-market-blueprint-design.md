# Vibe Coding Market 1.0 蓝图

日期：2026-06-13
状态：草案，等待用户审阅

## 1. 这个 Web 产品是什么

Vibe Coding Market 是一个偏公益性质的 vibe coding 项目学习站点，面向想用 Codex 做出真实 Web 项目的人。

它不是课程平台，不是训练营，不是付费产品，也不是项目市场。它更像一个经过策展的小型 Web 项目集合：每个项目都能在线体验、源码开放，并且有一份可以跟着 Codex 从 0 到 1 复现的操作文档。

核心用户路径是：

1. 在线体验一个已经完成的小项目。
2. 看懂这个项目的功能和复杂度来源。
3. 查看开源代码。
4. 跟着 Codex 操作文档从空文件夹复现项目。
5. 在原项目基础上做二创，变成自己的版本。

第一优先用户是完全编程小白。站点需要让他们感觉：“我好像真的可以跟着 Codex 做出这个东西。” 有一点前端基础的用户也应该能从中获得结构化练习，但第一版不应该假设用户已经理解前端工程化。

## 2. 产品定位

这个产品应该像一个高完成度的公开项目画廊，里面藏着一条新手学习路径。

它不应该像：

- 普通教程博客；
- 课程销售页；
- 白底卡片式 Web demo 集合；
- 设计工具或模板工具站；
- AI API 展示站；
- 社区平台。

它的核心价值不是“有几个实用工具”，而是：每个项目都好玩、好看、可交互、开源，并且能通过 Codex 被复现。

## 3. 1.0 在大路线中的位置

在 Vibe Coding Market 的整体路线里，1.0 是“路径验证版”。

它不是最终形态，也不需要解决项目规模化、贡献机制、社区反馈、复杂筛选或多路径推荐。1.0 只需要证明一件事：一个编程小白能不能通过少量高完成度项目，理解 vibe coding 的价值，并跟着 Codex 从 0 到 1 做出自己的第一个 Web 作品。

因此，1.0 的核心不是项目数量，而是闭环质量。

1.0 要验证：

- 项目是否足够吸引人，让用户愿意点开；
- 在线 demo 是否能让用户快速理解最终效果；
- 源码和文档是否能支撑用户复现；
- Codex 操作文档是否真的适合小白；
- 用户是否会产生二创和分享的冲动。

1.0 不负责：

- 建立完整项目库；
- 承载大量项目分类；
- 接纳外部投稿；
- 建立社区；
- 覆盖所有 vibe coding 场景。

这些是 2.0 和 3.0 才应该处理的问题。

## 4. 第一版范围

第一版只验证一条完整链路：

用户看到网站 -> 选择项目 -> 在线体验 -> 理解项目 -> 跟着 Codex 文档复现 -> 能做出大部分效果 -> 产生二创想法。

第一版应该包含：

- 一个首页；
- 一条很短的新手路径；
- 5 个精心选择的纯 Web 项目；
- 一个统一的项目详情页模板；
- 每个项目一个在线 demo；
- 每个项目一个源码入口；
- 每个项目一份 Codex 从 0 到 1 操作文档；
- 清晰的项目复杂度标签；
- 一个反馈或社交分享入口。

第一版不做：

- 登录、账号、用户中心；
- 后端服务、数据库服务、云函数；
- 第三方 API；
- AI 对话、AI 生成、模型 API；
- 付费、会员、转化漏斗；
- 项目投稿平台；
- 评论区、论坛、社区、排行榜；
- 复杂搜索和筛选；
- 多角色学习路径；
- 完整前端工程化课程。

## 5. 项目准入规则

第一版的每个项目都必须是纯 Web 项目。

允许：

- HTML、CSS、JavaScript；
- 页面内状态；
- localStorage；
- 必要时使用轻量前端库；
- 静态部署；
- 只有在明显有收益时才使用 Node 或 Vite。

避免：

- 后端 API；
- 托管数据库；
- 登录鉴权；
- 支付；
- 服务端文件上传；
- 第三方模型 API；
- 以视觉生成为核心功能；
- 复杂拖拽工作流；
- 需要大量解释的复杂图表；
- 第一版使用 WebGL 或重型动画系统。

判断一个项目是否适合第一版，不只看功能小不小，还要看它有没有隐藏复杂度。比如拖拽、音频同步、复杂移动端手势、复杂导出、复杂图表，都可能让小白卡住。

## 6. 视觉策略

第一版采用 “Studio Anthology / 设计选集型” 视觉策略。

站点外壳保持统一：导航、项目元信息、学习路径、源码入口、Codex 文档、复杂度拆解应该像一个产品。

项目 demo 允许拥有不同视觉人格。每个项目都应该像一个小型完成品，而不是同一套模板换颜色。

第一版视觉原则：

- 高完成度；
- 第一眼有吸引力；
- 功能实用，但视觉不能普通；
- 不默认使用白底卡片 SaaS 模板；
- 不把 Apple-like 当成唯一审美；
- 每个项目有自己的设计母题；
- 优先用 CSS、布局、动效、材质完成质感；
- 动效服务交互反馈和氛围，不做纯装饰。

这意味着：站点本身可以克制清楚，项目本身要有设计感。统一发生在学习结构里，个性发生在 demo 舞台里。

## 7. 第一版项目集合

推荐第一版项目如下：

| 顺序 | 项目 | 路径角色 | 视觉方向 | 主要学习点 |
| --- | --- | --- | --- | --- |
| 1 | 专注番茄钟 | 第一个实用小应用 | Solar Dial / 专注计时舱 | 计时器、状态切换、按钮、进度、本地记录 |
| 2 | 记忆翻牌小游戏 | 第一个游戏项目 | Neon Arcade Lab / 霓虹实验台 | 数组、随机、点击状态、匹配判断、得分 |
| 3 | 极简记账本 | 本地数据工具 | Receipt Ledger / 票据账房 | 表单、列表、分类、统计、localStorage |
| 4 | 习惯打卡日历 | 进度反馈工具 | Growth Grid / 生长网格 | 日期、日历网格、连续打卡、视觉反馈 |
| 5 | 预算 / 分摊计算器 | 场景型实用工具 | Split Console / 分账控制台 | 多项输入、自动计算、分组结果、分享摘要 |

这组项目的平衡点是：

- 有实用工具；
- 有游戏项目；
- 都可以纯 Web 实现；
- 都能做出明显设计感；
- 都有可解释的学习价值；
- 不需要后端、账号、API 或数据库；
- 不会立刻变成完整课程体系。

## 8. 游戏项目规划方向

第一版应该包含一个游戏项目，但游戏必须是小白友好的 Web 小游戏。

游戏项目规则：

- 单人游戏；
- 单页面；
- 不需要后端；
- 不做排行榜；
- 不做账号；
- 不做复杂物理；
- 不做复杂地图编辑器；
- 规则 10 秒内能理解；
- 3 分钟内能玩出反馈；
- 尽量兼容鼠标和触屏；
- 教学重点是状态、事件、分数、重开、反馈。

第一版推荐游戏是：记忆翻牌小游戏。

原因：

- 规则简单；
- 很容易做出漂亮视觉；
- 互动足够强；
- 可以教数组、随机排序、卡片状态、匹配逻辑、分数和重开；
- 避免物理、键盘兼容、移动端控制、碰撞检测等复杂问题。

后续可以探索的游戏方向：

- 反应速度挑战；
- 打字防线游戏；
- 小型迷宫冒险；
- 节奏点击挑战。

这些适合放到 V2 或更后面，因为它们会引入计时精度、键盘输入、移动端控制、碰撞逻辑、音频同步等额外复杂度。

## 9. 首页蓝图

首页第一屏只需要快速回答三个问题：

1. 这是什么？
2. 适合谁？
3. 我现在可以先做什么？

推荐首页结构：

1. 首屏 Hero
   - 标题：5 个纯 Web 小项目，带你用 Codex 从 0 做到可发布；
   - 副文案：面向编程小白，每个项目都能在线体验、查看源码、跟着 Codex 操作文档复现；
   - 主按钮：从第一个项目开始；
   - 次按钮：先看 5 个项目；
   - 标签：公益、开源、无需登录、无后端、可复现、适合小白。

2. 新手路径
   - 先玩：体验完成品；
   - 看懂：理解功能和复杂度；
   - 跟做：用 Codex 从空文件夹复现；
   - 二创：改成自己的版本。

3. 项目区
   - 展示 5 张项目卡；
   - 每张卡包含项目名、一句话效果、难度、预计复现时间、核心能力、在线体验入口、详情页入口。

4. 为什么公开
   - 免费开放，不卖课；
   - 源码、Prompt、过程尽量透明；
   - 每个项目都从空文件夹开始复现。

5. 反馈 / 分享
   - 鼓励用户体验、复现、二创，并把结果发到社交媒体收集反馈。

首页不需要过度解释 vibe coding。它应该让用户愿意先点进一个项目。

## 10. 项目详情页蓝图

每个项目详情页遵循统一结构：

1. 项目头部
   - 项目名；
   - 一句话说明；
   - 难度；
   - 预计时间；
   - 适合人群；
   - 操作按钮：在线体验、查看源码、跟着 Codex 做。

2. 在线体验
   - 放在页面靠前位置；
   - 用户先玩到结果，再读说明。

3. 你会学到什么
   - 用能力语言，而不是课程术语。

4. 复杂度从哪里来
   - 页面结构；
   - 交互；
   - 状态；
   - 数据；
   - 视觉完成度；
   - 部署或分享。

5. 源码导览
   - GitHub 仓库；
   - 文件结构；
   - 新手优先看哪些文件；
   - 哪些地方适合先改。

6. Codex 从 0 到 1 操作文档
   - 明确入口；
   - 可直接复制的 Prompt；
   - 每一步都有验收方式。

7. Prompt 区
   - 起步 Prompt；
   - 修改 Prompt；
   - 排错 Prompt。

8. 常见小白问题
   - 页面空白；
   - 样式没生效；
   - 按钮没反应；
   - 状态没有保存；
   - 手机布局乱了。

9. 二创任务
   - 轻改：改颜色、文案、主题；
   - 中改：加一个按钮、模式或状态；
   - 深改：换成另一个使用场景；
   - 发布挑战：把结果截图或录屏发出去。

## 11. Codex 操作文档标准

每份项目文档都要让小白始终知道：

- 我现在在哪里；
- 我要让 Codex 做什么；
- 做完之后应该发生什么；
- 我怎么判断成功；
- 如果失败了怎么办。

标准结构：

1. 项目目标；
2. 准备条件；
3. 从空文件夹开始；
4. 第一次 Prompt；
5. Codex 应该产出哪些文件；
6. 如何运行或打开项目；
7. 小白可理解的验收清单；
8. 分步骤改进；
9. 按现象组织的常见问题；
10. 二创 Prompt。

文档不应该变成长篇前端理论课。它要像一份可以跟着执行的 Codex 操作记录。

## 12. 第一版成功标准

第一版成功不是项目数量多，而是路径成立。

成功标准：

- 用户在首页第一屏能理解这个站点是什么；
- 小白能知道第一个该点哪个项目；
- 每个项目都能在线体验；
- 每个项目都有源码和 Codex 复现文档；
- 项目整体足够好看、好玩，适合公开发到社交媒体；
- 至少有用户能跟着文档复现出 70% 以上效果；
- 从社交反馈里能看出哪个项目最吸引人。

## 13. 1.0 到 2.0 的交接

1.0 完成后，不应该立刻追求更多功能，而应该先判断路径是否成立。

如果 1.0 被验证有效，2.0 再进入“路径扩展版”：增加更多项目，建立分类、难度、能力标签和多条推荐路径。

1.0 需要为 2.0 沉淀三类模板：

1. 项目详情页模板；
2. Codex 操作文档模板；
3. 项目元数据模板。

1.0 还需要给 2.0 留下这些判断：

- 哪类项目最吸引小白；
- 哪类项目最容易被复现；
- 哪些复杂度会让用户卡住；
- 哪种文档格式最有效；
- 哪个首发项目最适合作为后续路径的起点。

如果 1.0 没有验证出复现路径，就不应该急着扩展到 2.0。应该先修项目质量、文档质量和第一个项目体验。
