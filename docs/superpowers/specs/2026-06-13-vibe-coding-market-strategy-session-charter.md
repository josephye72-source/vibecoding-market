# Vibe Coding Market 战略 Session 章程

日期：2026-06-13
状态：草案，等待用户审阅

## 1. 这套 Session 的职责

这套 session 是 Vibe Coding Market 的战略控制台。

它负责定义和维护：

- 项目的终极目标；
- 项目的北极星；
- 1.0 / 2.0 / 3.0 版本路线；
- 每个版本的范围边界；
- 每个版本的验收标准；
- 执行过程中的关键 Review Gates；
- 当执行 session 产生方案或结果时，是否允许继续推进。

这套 session 不负责日常执行细节。它不应该下沉到完整代码实现、单个 UI 像素、具体组件细节、具体部署命令或每篇文档的逐字润色。

它的工作方式是：保持宏观判断，做版本级决策。

## 2. 与其他 Session 的分工

其他 session 可以负责具体执行，例如：

- 首页视觉方案；
- 项目详情页设计；
- 第一个项目 demo；
- 某个项目的源码实现；
- Codex 操作文档撰写；
- GitHub 仓库整理；
- 部署和发布；
- 社交媒体发布素材。

这些执行 session 完成关键产出后，需要回到本 session 做战略级 Review。

本 session 不要求重新做执行工作，但要判断：

- 是否符合大蓝图；
- 是否符合当前版本目标；
- 是否偏离公益、开源、可复现定位；
- 是否适合小白；
- 是否存在范围膨胀；
- 是否可以进入下一阶段。

## 3. 本 Session 不做什么

本 session 不做：

- 直接实现具体项目；
- 直接写完整前端代码；
- 直接制作单个项目高保真设计稿；
- 逐条修 UI 细节；
- 逐字编辑项目教程；
- 决定每个组件的最终样式；
- 处理部署故障；
- 维护项目仓库日常 issue；
- 做社交媒体具体发布排期。

如果讨论开始进入这些细节，应该把它们拆到新的执行 session。

## 4. Review 的基本原则

本 session 的 Review 不是为了追求完美，而是为了防止偏航。

所有 Review 都围绕四个问题：

1. 这个结果是否服务北极星？
2. 这个结果是否符合当前版本目标？
3. 这个结果是否让小白更容易完成“体验 -> 复现 -> 二创”？
4. 这个结果是否引入了不该在当前版本承担的复杂度？

如果一个结果在视觉上更酷，但让小白更难复现，应该谨慎。

如果一个结果功能更完整，但引入后端、账号、数据库或复杂服务，1.0 应该拒绝。

如果一个结果看起来像课程销售页、训练营入口或 SaaS 产品，应当回退。

## 5. 1.0 Review Gates

1.0 是路径验证版。它的 Review Gates 应该尽量少，但必须卡住关键风险。

### Gate 1：项目清单 Review

目的：确认 1.0 的 5 个项目仍然符合路径验证目标。

通过标准：

- 每个项目都是纯 Web；
- 不需要后端、数据库、登录、第三方 API；
- 至少一个项目是游戏；
- 项目整体有实用性和吸引力；
- 每个项目都有明确学习点；
- 项目复杂度适合小白或可以被文档拆解。

拒绝信号：

- 项目需要服务端能力；
- 项目本质变成 AI API 或视觉生成工具；
- 项目看起来简单但隐藏复杂度过高；
- 项目只是技术练习，没有用户想玩的成品感。

### Gate 2：首页与信息架构 Review

目的：确认首页能让小白快速理解网站，并进入第一个项目。

通过标准：

- 第一屏能说明这是什么；
- 用户能知道自己适不适合；
- 用户能找到第一个项目入口；
- 路径表达是“先玩、看懂、跟做、二创”；
- 页面不像课程销售页；
- 页面不像普通项目列表。

拒绝信号：

- 过度解释 vibe coding；
- 过度强调课程、训练营、体系化学习；
- 项目入口被品牌叙事淹没；
- 用户不知道下一步该点哪里。

### Gate 3：视觉策略 Review

目的：确认 Studio Anthology 策略成立。

通过标准：

- 站点外壳统一、清楚；
- 项目 demo 各自有视觉主题；
- 整体有高完成度；
- 不只是 Apple-like；
- 不只是白底卡片 SaaS 模板；
- 视觉服务项目理解和互动体验。

拒绝信号：

- 所有项目看起来像同一个模板换色；
- 视觉炫技超过项目本身；
- 过度使用重型 3D、WebGL、复杂动画；
- 视觉方向让项目更难复现。

### Gate 4：第一个项目原型 Review

目的：用第一个项目验证整套方法，而不是同时推进 5 个项目。

通过标准：

- demo 可以直接体验；
- 功能边界清楚；
- 视觉完成度足够对外展示；
- 小白能理解项目目标；
- 源码结构可以解释；
- 有初版 Codex 操作文档；
- 有二创方向。

拒绝信号：

- 项目功能膨胀；
- demo 只是半成品；
- 源码无法导览；
- 文档无法让人复现；
- 视觉好看但实现复杂度不可解释。

### Gate 5：Codex 文档 Review

目的：确认文档不是教程文章，而是可执行的 Codex 复现路径。

通过标准：

- 从空文件夹开始；
- 每一步都有 Prompt；
- 每一步有预期产出；
- 每一步有验收方式；
- 有常见失败处理；
- 有二创 Prompt；
- 小白能知道自己在哪里、下一步做什么。

拒绝信号：

- 文档只讲概念；
- 文档假设用户懂前端；
- Prompt 不完整；
- 没有失败处理；
- 没有验收清单；
- 用户无法判断自己是否做对。

### Gate 6：1.0 Release Review

目的：判断 1.0 是否可以公开发布并收集反馈。

通过标准：

- 5 个项目都能在线体验；
- 5 个项目都有源码入口；
- 5 个项目都有 Codex 操作文档；
- 首页表达清楚；
- 项目详情页结构一致；
- 不存在明显范围膨胀；
- 适合发到社交媒体；
- 有反馈入口或反馈方式。

拒绝信号：

- demo 无法正常体验；
- 源码或文档缺失；
- 有项目明显不符合纯 Web 约束；
- 站点表达像课程销售或商业转化；
- 发布后无法判断用户反馈。

### Gate 7：1.0 Feedback Review

目的：从真实反馈判断是否进入 2.0。

通过标准：

- 能看出哪个项目最吸引人；
- 能看出用户在哪一步卡住；
- 至少有人尝试复现或表达复现意愿；
- 能判断文档模板是否有效；
- 能判断 2.0 应优先扩哪类项目。

拒绝信号：

- 只有浏览，没有复现信号；
- 用户看不懂站点定位；
- 项目好看但没人愿意跟做；
- 文档被认为难以执行；
- 反馈无法指导下一步。

## 6. 2.0 Review Gates

2.0 是路径扩展版。它的重点是从单条路径扩展到多条路径。

### Gate 1：项目扩展 Review

通过标准：

- 新项目仍然符合内容扩展原则；
- 项目数量增加但质量不下降；
- 每个项目都有元数据；
- 每个项目都能归入明确路径或分类；
- 新项目复用 1.0 的文档模板。

### Gate 2：路径结构 Review

通过标准：

- 用户能按兴趣或能力选择项目；
- 难度层级清楚；
- 能力标签可理解；
- 路径不是课程大纲，而是项目选择辅助；
- 游戏路径、工具路径等边界清楚。

### Gate 3：筛选与导航 Review

通过标准：

- 筛选足够轻；
- 不需要账号；
- 不需要复杂搜索系统；
- 用户能快速找到适合自己的项目；
- 不牺牲首页的清晰表达。

### Gate 4：2.0 Release Review

通过标准：

- 12-20 个项目或相当规模的项目库已经有组织；
- 至少 2-3 条路径成立；
- 新项目没有稀释整体质量；
- 文档体系仍然可维护；
- 用户二创或反馈开始出现。

## 7. 3.0 Review Gates

3.0 是开放生态版。它的重点不是变成重社区，而是让项目地图可以持续生长。

### Gate 1：贡献机制 Review

通过标准：

- 有项目贡献指南；
- 有项目提案模板；
- 有 Codex 过程记录模板；
- 有质量标准；
- 外部贡献不会降低项目整体质量。

### Gate 2：二创展示 Review

通过标准：

- 二创案例能帮助新用户理解可能性；
- 展示方式轻量；
- 不需要复杂账号系统；
- 不引入社区运营负担；
- 不让站点偏离学习和复现。

### Gate 3：高级项目分层 Review

通过标准：

- 纯 Web 项目仍然是核心；
- API / 后端 / AI 项目被放入进阶区；
- 依赖、风险和门槛清楚标注；
- 小白默认路径不受干扰。

### Gate 4：3.0 Release Review

通过标准：

- 项目地图可以持续扩展；
- 外部贡献有入口但不失控；
- 用户能看到从入门到进阶的路径；
- 贡献质量可以被审核；
- Vibe Coding Market 仍然是公开、公益、可复现的项目地图。

## 8. 执行 Session 回到本 Session 时需要带什么

执行 session 回来做 Review 时，至少要带：

- 本次执行目标；
- 相关产出链接或文件；
- 它对应哪个版本和哪个 Review Gate；
- 已完成的内容；
- 未完成或有风险的内容；
- 需要本 session 决策的问题。

如果是设计产出，需要带：

- 设计目标；
- 关键页面或状态；
- 视觉方向说明；
- 与 Studio Anthology 的关系；
- 对小白路径的影响；
- 可能的实现复杂度。

如果是项目 demo，需要带：

- 在线体验方式；
- 源码位置；
- 功能范围；
- 复杂度拆解；
- 是否纯 Web；
- 文档状态；
- 已知问题。

如果是 Codex 文档，需要带：

- 项目目标；
- 起步 Prompt；
- 关键步骤；
- 验收清单；
- 失败处理；
- 二创任务。

## 9. 决策记录规则

这套 session 做出的重要决策应该沉淀到文档中。

需要记录的决策包括：

- 版本范围变化；
- 项目清单变化；
- 游戏规划变化；
- Review Gate 变化；
- 1.0 是否进入 2.0；
- 2.0 是否进入 3.0；
- 明确拒绝某类方向。

不需要记录的内容包括：

- 临时想法；
- 单个 UI 细节；
- 执行 session 内部过程；
- 已被否定且不影响路线的尝试。

## 10. 本 Session 的完成标准

这套 strategy session 的基础目标完成时，应该已经有：

- 大蓝图与版本路线图；
- 1.0 蓝图；
- Strategy Session Charter；
- 1.0 / 2.0 / 3.0 的版本级 Review Gates；
- 明确的执行 session 回流规则。

之后这套 session 可以继续长期存在，用来做版本级决策和验收。
