## 1. 文档目的

这份 Spec 是 Vibe Coding Market 1.0 的执行基准。后续首页设计、视觉探索、项目 demo、项目详情页、源码整理、Codex 文档、发布验收，都应以本文件为准。

本文件不替代战略文件。战略文件定义方向，本文件定义 V1 如何落地、分几个阶段推进、每个核心交付物如何验收。

前端设计质量工具链记录在 `docs/superpowers/specs/2026-06-13-vibe-coding-market-frontend-quality-tooling.md`。执行首页、项目 demo、项目详情页和视觉 Review 时，应优先参考该工具链，但最终验收仍以本 Spec 为准。

本文件的约束重点是：

- 阶段清楚；
- 交付物清楚；
- 验收标准可量化；
- 视觉设计感不能降级；
- 用户交互感不能降级；
- 不能提前引入 2.0 / 3.0 的复杂度。

视觉设计感和用户交互感是本项目的重点验收维度，但不是唯一验收维度。V1 仍然必须同时满足项目完整性、纯 Web 范围控制、源码清晰度、Codex 文档可执行性、小白可复现性、反馈闭环、响应式可用性和发布稳定性。任何执行 session 不得把用户特别强调的视觉与交互理解为可以忽略其他质量要求。

## 2. 顶层原则

Vibe Coding Market 1.0 是路径验证版，不是项目库完整版。

1.0 必须验证一条完整链路：

用户看到网站 -> 选择一个项目 -> 在线体验 -> 看懂复杂度 -> 查看源码 -> 跟 Codex 文档复现 -> 产生二创想法。

V1 的最高优先级不是访问量、项目数量或功能完整度，而是：

一个编程小白能否通过这里的项目，用 Codex 做出自己的第一个可发布 Web 作品。

## 3. V1 范围

### 3.1 必须包含

- 1 个首页；
- 1 条短的新手路径表达；
- 5 个首发纯 Web 项目；
- 5 个在线 demo；
- 5 个项目详情页；
- 5 个源码入口；
- 5 份 Codex 从 0 到 1 复现文档；
- 5 组复杂度拆解；
- 5 组源码导览；
- 5 组常见问题；
- 5 组二创任务；
- 1 套项目元数据模板；
- 1 个轻量反馈入口。

### 3.2 明确不做

V1 不做以下内容：

- 登录、账号、用户中心；
- 后端服务、数据库、云函数；
- 第三方 API、AI API、模型 API；
- 付费、会员、商业转化漏斗；
- 项目投稿平台；
- 评论区、论坛、排行榜；
- 复杂搜索、复杂筛选、多路径推荐；
- 完整课程体系；
- 重型 WebGL、复杂 3D、复杂动画系统；
- 需要大量素材管理、拖拽工作流、音频同步、文件上传或复杂导出的项目。

## 4. 首发项目清单

V1 锁定 5 个首发项目：

| 顺序 | 项目 | 路径角色 | 视觉母题 | 核心学习点 |
| --- | --- | --- | --- | --- |
| 1 | 专注番茄钟 | 第一个实用小应用 | Solar Dial / 专注计时舱 | 计时器、状态切换、按钮、进度、本地记录 |
| 2 | 记忆翻牌小游戏 | 第一个游戏项目 | Neon Arcade Lab / 霓虹实验台 | 数组、随机、点击状态、匹配判断、得分 |
| 3 | 极简记账本 | 本地数据工具 | Receipt Ledger / 票据账房 | 表单、列表、分类、统计、localStorage |
| 4 | 习惯打卡日历 | 进度反馈工具 | Growth Grid / 生长网格 | 日期、日历网格、连续打卡、视觉反馈 |
| 5 | 预算 / 分摊计算器 | 场景型实用工具 | Split Console / 分账控制台 | 多项输入、自动计算、分组结果、分享摘要 |

项目清单变更必须回到战略层做 Gate 1 Review。

## 5. 阶段划分

### 阶段 0：范围冻结与基准确认

目标：确认 V1 的范围、首发项目、非目标和验收口径。

入口条件：

- 三份战略文件已经存在；
- 本基准 Spec 已经创建；
- 用户认可 V1 先做路径验证，不做平台化扩展。

核心交付物：

- V1 首发项目清单；
- V1 非目标清单；
- V1 阶段划分；
- V1 核心交付物验收标准。

出口验收标准：

- 5 个首发项目全部明确，数量不得少于 5 个，也不得多于 5 个；
- 5 个项目全部满足纯 Web 约束；
- 至少 1 个项目是游戏；
- 所有非目标被明确写入文档；
- 后续执行 session 能从本文件判断自己对应哪个阶段和哪个交付物。

对应战略 Gate：

- Gate 1：项目清单 Review。

### 阶段 1：首页与信息架构

目标：让用户第一屏理解站点，并能进入第一个项目。

核心交付物：

- 首页信息架构；
- 新手路径模块；
- 项目卡片结构；
- 项目详情页结构；
- 项目元数据字段。

出口验收标准：

- 首页第一屏必须回答 3 个问题：这是什么、适合谁、下一步做什么；
- 第一屏必须包含 1 个主行动入口“从第一个项目开始”；
- 第一屏必须包含 1 个次行动入口“先看 5 个项目”；
- 首页必须展示“先玩、看懂、跟做、二创”四步路径；
- 首页项目区必须展示 5 张项目卡；
- 每张项目卡必须包含项目名、一句话效果、难度、预计复现时间、核心能力、在线体验入口、详情页入口；
- 项目详情页结构必须包含 9 个固定区块：项目头部、在线体验、你会学到什么、复杂度来源、源码导览、Codex 文档、Prompt 区、常见问题、二创任务；
- 首页不得出现课程售卖、训练营、限时转化、会员权益等表达。

对应战略 Gate：

- Gate 2：首页与信息架构 Review。

### 阶段 2：视觉系统与交互原则

目标：确认 Studio Anthology 视觉策略可以被执行，并把视觉设计感和用户交互感变成硬性验收条件。

核心交付物：

- 站点级视觉外壳方向；
- 5 个项目 demo 的视觉母题说明；
- 站点交互原则；
- 项目 demo 交互原则；
- 视觉与交互验收清单。

出口验收标准：

- 站点外壳必须有统一的导航、按钮、标签、项目卡、详情页信息结构；
- 5 个项目 demo 必须各有独立视觉母题；
- 每个项目 demo 至少在 3 个维度上区别于其他项目：色彩、布局、材质、动效、图形语言、空间感、组件形态；
- 不允许 5 个项目看起来像同一套模板换色；
- 所有主要按钮和可点击控件必须具备默认、悬停或触摸反馈、聚焦、按下后的反馈状态；
- 移动端主要点击目标尺寸不得小于 44px x 44px；
- 核心交互反馈必须在用户操作后 100ms 内出现视觉反馈；
- 页面在 390px、768px、1440px 宽度下不得出现主要文本遮挡、按钮溢出、核心控件不可见；
- 不允许使用重型 WebGL、复杂 3D 或为了炫技而增加小白无法复现的动画系统；
- 视觉必须服务项目理解和互动体验，而不是只做装饰。

对应战略 Gate：

- Gate 3：视觉策略 Review。

### 阶段 3：第一个项目闭环原型

目标：用“专注番茄钟”验证完整项目闭环。

核心交付物：

- 专注番茄钟在线 demo；
- 专注番茄钟项目详情页；
- 专注番茄钟源码入口；
- 专注番茄钟源码导览；
- 专注番茄钟 Codex 从 0 到 1 文档；
- 专注番茄钟常见问题；
- 专注番茄钟二创任务。

出口验收标准：

- demo 必须可直接体验；
- demo 必须包含开始、暂停、重置、状态切换、进度反馈、本地记录 6 类核心功能；
- demo 不得依赖后端、数据库、登录或第三方 API；
- 项目详情页必须完整使用 9 个固定区块；
- Codex 文档必须从空文件夹开始；
- Codex 文档必须包含至少 1 个起步 Prompt、3 个分步改进 Prompt、3 个排错 Prompt、3 个二创 Prompt；
- 每个 Prompt 必须配套预期产出和验收方式；
- 源码导览必须说明新手优先看哪些文件、哪些区域适合先改；
- 二创任务必须包含轻改、中改、深改三个层级；
- 小白视角 walkthrough 必须能在不阅读前端理论的情况下理解项目目标、核心交互和下一步操作。

对应战略 Gate：

- Gate 4：第一个项目原型 Review；
- Gate 5：Codex 文档 Review 的首个样本。

### 阶段 4：模板固化

目标：把第一个项目沉淀成后续 4 个项目可复用的模板。

核心交付物：

- 项目详情页模板；
- Codex 文档模板；
- 项目元数据模板；
- 单项目 Definition of Done；
- demo、源码、文档、详情页之间的链接规则。

出口验收标准：

- 项目详情页模板必须覆盖 9 个固定区块；
- Codex 文档模板必须覆盖 10 个固定区块：项目目标、准备条件、从空文件夹开始、第一次 Prompt、预期文件、运行方式、验收清单、分步改进、常见问题、二创 Prompt；
- 项目元数据模板必须包含项目名、slug、顺序、路径角色、一句话说明、难度、预计复现时间、核心能力、视觉母题、在线 demo 链接、源码链接、文档链接；
- 链接规则必须保证用户从首页、详情页、demo、源码、文档之间能形成闭环；
- 后续 4 个项目不得绕开模板自行发明新的学习结构。

对应战略 Gate：

- Gate 5：Codex 文档 Review。

### 阶段 5：剩余四个项目批量交付

目标：用固化模板完成剩余 4 个项目，并保持项目质量一致。

执行顺序：

1. 记忆翻牌小游戏；
2. 极简记账本；
3. 习惯打卡日历；
4. 预算 / 分摊计算器。

核心交付物：

- 4 个在线 demo；
- 4 个项目详情页；
- 4 个源码入口；
- 4 份源码导览；
- 4 份 Codex 从 0 到 1 文档；
- 4 组常见问题；
- 4 组二创任务。

出口验收标准：

- 每个项目都必须满足“单项目 Definition of Done”；
- 5 个项目最终必须全部可在线体验；
- 5 个项目最终必须全部有源码入口；
- 5 个项目最终必须全部有 Codex 文档；
- 5 个项目最终必须全部有视觉母题且互不混同；
- 每个项目必须至少包含 3 个清晰交互状态，例如空状态、输入或进行中状态、完成或结果状态；
- 每个项目必须至少包含 1 个本地状态或页面状态变化，让用户能感知“我操作后发生了变化”；
- 所有项目在桌面和移动端都必须完成核心体验；
- 任一项目不得因为视觉设计引入小白难以理解的复杂实现。

对应战略 Gate：

- Gate 6：1.0 Release Review 的前置条件。

### 阶段 6：站点整合与发布前验收

目标：判断 V1 是否可以公开发布并收集反馈。

核心交付物：

- 完整首页；
- 5 个完整项目详情页；
- 5 个可体验 demo；
- 5 个源码入口；
- 5 份 Codex 文档；
- 反馈入口；
- 发布前验收记录；
- 发布风险清单。

出口验收标准：

- 首页所有项目入口均可点击，且跳转目标正确；
- 5 个 demo 均可完成核心体验；
- 5 个源码入口均可访问；
- 5 个 Codex 文档入口均可访问；
- 5 个项目详情页结构一致；
- 页面在 390px、768px、1440px 宽度下完成检查，无核心内容重叠或不可点击；
- 连续 5 分钟手动体验站点和 demo，不出现阻断型错误；
- 浏览器控制台不得出现影响核心体验的错误；
- 反馈入口必须能让用户提交或表达 4 类信息：最感兴趣项目、是否愿意复现、卡住位置、二创想法；
- 站点表达不得像课程销售页、训练营入口、SaaS 产品或普通 demo 列表。

对应战略 Gate：

- Gate 6：1.0 Release Review。

### 阶段 7：发布后反馈 Review

目标：用真实反馈判断是否进入 2.0。

核心交付物：

- 1.0 反馈汇总；
- 项目吸引力排序；
- 文档卡点记录；
- 复现信号记录；
- 2.0 进入建议。

出口验收标准：

- 至少收集到 5 条有效外部反馈，或至少完成 2 次小白复现观察；
- 有效反馈必须包含项目偏好、复现意愿、卡点或二创想法中的至少 2 类信息；
- 至少识别出 1 个最吸引人的项目；
- 至少识别出 1 个最容易让用户卡住的步骤；
- 至少有 1 个用户尝试复现，或明确表达复现意愿；
- 如果没有复现信号，不进入 2.0，优先修项目质量、文档质量和第一个项目体验；
- 如果有人能复现 70% 以上效果，记录其使用的项目、耗时、卡点和缺失部分。

对应战略 Gate：

- Gate 7：1.0 Feedback Review。

## 6. 核心交付物验收标准

### 6.1 首页

首页通过验收必须同时满足：

- 第一屏包含站点名称或清晰标题；
- 第一屏用一句主文案说明“5 个纯 Web 小项目，带你用 Codex 从 0 做到可发布”这一类价值；
- 第一屏包含主按钮和次按钮；
- 第一屏包含至少 4 个定位标签：公益、开源、无需登录、无后端、可复现、适合小白中的任意 4 个；
- 首页必须展示 4 步路径：先玩、看懂、跟做、二创；
- 首页必须展示 5 个项目卡；
- 首页必须有反馈或分享入口；
- 用户从首页进入第一个项目的点击路径不得超过 1 次；
- 用户从首页进入任意项目详情页的点击路径不得超过 1 次；
- 首页不得包含课程价格、报名、优惠、名额、会员、训练营等销售表达。

### 6.2 项目卡片

每张项目卡通过验收必须同时满足：

- 项目名存在；
- 一句话效果说明存在，长度不超过 30 个中文字符；
- 难度存在，使用 1-3 级；
- 预计复现时间存在，使用分钟或小时表达；
- 核心能力标签数量为 3-5 个；
- 在线体验入口存在；
- 详情页入口存在；
- 视觉上能看出项目类别或主题，不只是文字列表。

### 6.3 项目详情页

每个项目详情页通过验收必须同时满足：

- 包含 9 个固定区块；
- 在线体验区位于页面前半部分；
- 项目头部包含项目名、一句话说明、难度、预计时间、适合人群、在线体验、查看源码、跟着 Codex 做；
- “你会学到什么”必须使用能力语言，不使用大段课程术语；
- “复杂度从哪里来”至少覆盖页面结构、交互、状态、数据、视觉完成度 5 类；
- “源码导览”必须指出新手优先看的文件；
- “Prompt 区”至少包含起步、修改、排错 3 类 Prompt；
- “常见问题”至少包含 5 个小白常见问题；
- “二创任务”至少包含轻改、中改、深改 3 个层级。

### 6.4 在线 Demo

每个 demo 通过验收必须同时满足：

- 可在浏览器中直接体验；
- 核心体验不需要登录；
- 核心体验不需要网络请求、后端、数据库或第三方 API；
- 首次打开 3 秒内必须出现项目标题、核心操作区和至少 1 个主要操作控件；
- 用户 15 秒内能找到第一个可操作控件；
- 用户 3 分钟内能完成一次核心体验或看到明确结果；
- 至少有 3 个可命名交互状态，并在详情页或源码导览中写明这些状态的名称；
- 所有主要操作都有即时视觉反馈；
- 刷新页面后，涉及本地记录的项目必须保留关键数据；
- 移动端宽度 390px 下核心操作可用；
- 桌面宽度 1440px 下核心交互区域必须位于首屏中心区域，主要内容最大宽度不得超过 1200px；
- 连续操作 5 分钟不出现阻断型错误。

### 6.5 源码入口与源码导览

每个项目源码入口和源码导览通过验收必须同时满足：

- 有可访问源码入口；
- 源码结构能被新手解释；
- 导览中列出新手优先看的文件；
- 导览中说明每个核心文件负责什么；
- 导览中说明 3 个适合新手先改的位置；
- 导览不得假设用户已经理解完整前端工程化；
- 如果使用构建工具，必须解释为什么使用以及如何运行。

### 6.6 Codex 复现文档

每份 Codex 复现文档通过验收必须同时满足：

- 从空文件夹开始；
- 包含项目目标；
- 包含准备条件；
- 包含第一次可复制 Prompt；
- 包含 Codex 应该产出的文件清单；
- 包含运行或打开项目的方法；
- 包含至少 5 条小白可理解的验收清单；
- 包含至少 3 个分步改进 Prompt；
- 包含至少 3 个按现象组织的排错 Prompt；
- 包含至少 3 个二创 Prompt；
- 每一步都说明预期产出；
- 每一步都说明如何判断成功；
- 不写成长篇前端理论课。

### 6.7 视觉设计感

V1 的视觉设计通过验收必须同时满足：

- 站点外壳统一，项目 demo 个性化；
- 首页不是白底卡片式 demo 集合；
- 站点不像 SaaS 后台、课程销售页或模板站；
- 每个项目有命名视觉母题；
- 每个项目至少有 3 个视觉差异维度；
- 每个项目至少有 1 个服务交互的动效或状态变化；
- 字体、间距、颜色、按钮、标签在站点层保持一致；
- 项目 demo 可以使用不同风格，但详情页学习结构必须一致；
- 视觉不能靠复杂 WebGL、重型 3D 或难复现资产堆砌；
- 每个项目必须具备可截图传播的完成态：截图中能同时看到项目名称或核心界面、主要结果状态、独立视觉母题。

### 6.8 用户交互感

V1 的用户交互通过验收必须同时满足：

- 所有主要按钮可点击且有反馈；
- 所有输入控件有可见标签或明确上下文；
- 所有表单类项目有空状态、输入后状态、结果状态；
- 所有保存类项目刷新后能验证数据是否保存；
- 所有结果类项目能在用户操作后立即更新结果；
- 游戏项目打开后 10 秒内必须能看到目标、操作对象和反馈方式；
- 游戏项目 3 分钟内能得到明确反馈；
- 鼠标和触屏都能完成核心操作；
- 键盘 Tab 能定位到主要交互控件；
- 聚焦状态可见；
- 主要触摸目标不小于 44px x 44px。

### 6.9 反馈入口

反馈入口通过验收必须同时满足：

- 至少提供 1 个明确反馈渠道；
- 默认目标反馈渠道为 GitHub Issue；
- 如果公开 GitHub 仓库尚未准备好，使用公开社交话题作为临时反馈渠道；
- 反馈入口必须询问或引导用户表达 4 类信息：最感兴趣项目、是否愿意复现、卡住位置、二创想法；
- 首页和项目详情页都必须能找到反馈入口；
- 反馈入口不能变成社区系统、评论区或账号系统。

## 7. 单项目 Definition of Done

一个项目只有同时满足以下条件，才算 V1 可交付：

- demo 可直接体验；
- demo 完成核心功能闭环；
- demo 具备明确视觉母题；
- demo 不依赖后端、数据库、登录或第三方 API；
- demo 支持桌面和移动端核心操作；
- 项目详情页完整；
- 源码入口存在；
- 源码导览存在；
- 复杂度拆解存在；
- Codex 复现文档存在；
- 文档每一步都有 Prompt、预期产出、验收方式；
- 常见问题不少于 5 个；
- 二创任务不少于 3 个；
- 项目元数据完整；
- 项目没有引入 V1 非目标。

## 8. 项目级验收标准

### 8.1 专注番茄钟

必须满足：

- 支持开始、暂停、重置；
- 支持专注和休息至少 2 种状态；
- 显示倒计时；
- 显示进度反馈；
- 完成一次计时后有明确完成反馈；
- 保存至少一类本地记录，例如今日完成次数；
- 刷新后本地记录仍在；
- 视觉呈现符合 Solar Dial / 专注计时舱母题；
- 用户 15 秒内能理解如何开始。

### 8.2 记忆翻牌小游戏

必须满足：

- 至少包含 12 张牌、6 组配对；
- 每局开始时卡牌顺序随机；
- 支持翻牌、匹配判断、匹配成功反馈、匹配失败反馈；
- 显示步数或得分；
- 全部匹配完成后有胜利反馈；
- 支持重新开始；
- 鼠标和触屏都能操作；
- 视觉呈现符合 Neon Arcade Lab / 霓虹实验台母题；
- 游戏打开后 10 秒内必须能看到目标、操作对象和反馈方式，3 分钟内可完成或得到明确反馈。

### 8.3 极简记账本

必须满足：

- 支持添加收入或支出记录；
- 每条记录至少包含金额、分类、说明或日期中的 3 类信息；
- 至少提供 3 个分类；
- 支持删除记录；
- 显示总收入、总支出或结余中的至少 2 类统计；
- 数据保存到 localStorage；
- 刷新后记录仍在；
- 空状态必须包含 1 句提示文案和 1 个主要操作入口；
- 视觉呈现符合 Receipt Ledger / 票据账房母题。

### 8.4 习惯打卡日历

必须满足：

- 显示一个日历或网格，并且每个日期格必须能区分未打卡、已打卡、当前日期 3 类状态中的至少 2 类；
- 支持对当天或指定日期打卡；
- 打卡状态有明确视觉反馈；
- 显示连续打卡或本月完成数量中的至少 1 类统计；
- 数据保存到 localStorage；
- 刷新后打卡状态仍在；
- 至少包含空状态、已打卡状态、连续反馈状态；
- 视觉呈现符合 Growth Grid / 生长网格母题。

### 8.5 预算 / 分摊计算器

必须满足：

- 支持输入总金额或多项费用；
- 支持输入人数或参与者；
- 自动计算人均金额或分摊结果；
- 修改输入后结果立即更新；
- 支持生成一段可复制的结果摘要；
- 对无效输入必须显示提示文案，并阻止生成错误结果；
- 不需要账号、后端或支付能力；
- 视觉呈现符合 Split Console / 分账控制台母题；
- 用户 1 分钟内能完成一次分摊计算。

## 9. 质量检查方式

每个阶段交付前必须完成对应检查：

- 文档检查：确认无空章节、无未解释缩写、无只写概念不写验收的段落；
- 链接检查：确认首页、详情页、demo、源码、文档入口可访问；
- 响应式检查：390px、768px、1440px 三档宽度；
- 交互检查：主要按钮、输入、状态变化、保存、重置、结果展示；
- 视觉检查：站点统一性、项目差异性、是否像模板换色；
- 小白检查：用户是否知道自己在哪里、能做什么、下一步是什么；
- 范围检查：确认没有登录、后端、数据库、API、社区、投稿、排行榜等 V1 非目标。

## 10. 执行 Session 回流要求

任何执行 session 回到战略层或项目管理层 Review 时，必须带回：

- 本次目标；
- 对应阶段；
- 对应战略 Gate；
- 产出链接或文件；
- 已完成内容；
- 未完成内容；
- 风险点；
- 是否触碰 V1 非目标；
- 是否满足本 Spec 中对应交付物验收标准；
- 需要用户或战略层决策的问题。

设计类产出还必须补充：

- 视觉母题；
- 关键页面或状态；
- 与 Studio Anthology 策略的关系；
- 对小白复现难度的影响；
- 是否引入难以解释的视觉复杂度。

项目 demo 类产出还必须补充：

- 核心体验路径；
- 是否纯 Web；
- 本地状态或数据策略；
- 移动端可用性；
- 已知交互问题。

Codex 文档类产出还必须补充：

- 起步 Prompt；
- 分步 Prompt；
- 验收清单；
- 常见失败处理；
- 二创 Prompt。

## 11. 变更控制

以下变更必须回到战略层确认：

- 替换 5 个首发项目中的任意一个；
- 增加第 6 个首发项目；
- 引入后端、数据库、登录、第三方 API 或 AI API；
- 改变 V1 的发布验收标准；
- 删除 Codex 复现文档；
- 删除源码入口；
- 放弃“先体验、看懂、跟做、二创”的路径表达；
- 让项目视觉复杂度超过 Codex 文档可解释范围，例如依赖重型 3D、复杂 WebGL、不可复用私有素材或无法拆成步骤的动画系统。

以下变更可以由执行 session 内部决定：

- 单个 demo 的具体文案；
- 单个项目的颜色微调；
- 非核心布局细节；
- 不改变模板结构的局部组件调整；
- 不影响验收标准的文件组织优化。

## 12. 发布判定

V1 只有在以下条件全部满足时，才能建议公开发布：

- 阶段 0-6 全部完成；
- 5 个项目全部达到单项目 Definition of Done；
- 首页达到首页验收标准；
- 项目详情页达到详情页验收标准；
- Codex 文档达到文档验收标准；
- 视觉设计达到视觉验收标准；
- 用户交互达到交互验收标准；
- 反馈入口可用；
- 不存在 V1 非目标；
- 发布前风险清单没有阻断项。

发布后是否进入 2.0，不由项目数量决定，只由反馈 Review 决定。

如果发布后没有复现信号，先修 V1，不进入 2.0。

如果发布后能证明至少 1 个小白复现出 70% 以上效果，并且反馈能指出项目吸引力和文档卡点，才建议讨论 2.0。
