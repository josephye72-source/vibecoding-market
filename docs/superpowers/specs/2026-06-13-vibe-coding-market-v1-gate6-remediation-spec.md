# Vibe Coding Market V1 Gate 6 Remediation Spec

日期：2026-06-13
状态：生效，作为 Gate 6 复验前的执行 Spec
上游依据：

- `docs/reviews/acceptance/2026-06-13-v1-gate6-release-acceptance-report.md`
- `docs/superpowers/specs/2026-06-13-vibe-coding-market-v1-blueprint-revision-01.md`
- `docs/superpowers/specs/2026-06-13-vibe-coding-market-v1-baseline-spec.md`

## 1. 文档目的

这份 Spec 迭代旧 V1 基准 Spec，用来指导当前 release candidate 进入下一次 Gate 6 复验。

旧 V1 基准 Spec 仍保留为历史执行基线和细节参考；当旧 Spec 与 V1 蓝图修订版 01 或本文件冲突时，以 V1 蓝图修订版 01 和本文件为准。

本轮修复的目标不是扩展 V2，也不是重做整个产品，而是修复 Gate 6 明确指出的发布阻塞项：

- 长期产品定位；
- 整站信息架构；
- 真实源码入口；
- 反馈入口策略；
- 默认中文体验；
- 英文切换能力；
- 中文优先复现文档；
- 发布复验证据。

## 2. 当前发布判定

当前 V1 状态：release candidate，不建议公开发布。

当前 V1 技术质量可作为基础继续迭代，但不能以旧 `docs/reviews/2026-06-13-v1-release-review.md` 的 Pass 建议作为公开发布依据。公开发布判定以 `docs/reviews/acceptance/2026-06-13-v1-gate6-release-acceptance-report.md` 以及后续复验报告为准。

## 3. 优先级规则

后续执行按以下优先级判断冲突：

1. 大蓝图与北极星；
2. `2026-06-13-vibe-coding-market-v1-blueprint-revision-01.md`；
3. 本 Gate 6 Remediation Spec；
4. 旧 V1 baseline spec；
5. 具体实现计划；
6. 当前代码实现。

## 4. 修订后的 V1 目标

V1 的目标不是证明“我们做了 5 个项目”。

V1 的目标是：用 5 个高完成度纯 Web 项目验证 Vibe Coding Market 作为公开、公益、可复现的 vibe coding 项目地图是否成立。

用户在 V1 中必须能完成这条路径：

想法 -> 选择项目 -> 在线体验 -> 看源码 -> 看懂复杂度 -> 跟 Codex 复现 -> 二创 -> 反馈。

## 5. 复验前阶段划分

### 阶段 R0：产品基线重置

目标：把所有执行者从旧 release pass 口径切换到 Gate 6 remediation 口径。

核心交付物：

- 本 Spec；
- Gate 6 remediation implementation plan；
- 旧 release review 的历史状态说明；
- 旧 baseline spec / plan 的修订指向说明。

出口验收标准：

- 新增 Spec 明确引用 Gate 6 不通过报告和蓝图修订版 01；
- 旧 baseline spec 顶部明确说明其不再单独决定产品表达；
- 旧 implementation plan 顶部明确说明其已完成且不再作为下一轮执行计划；
- 新 plan 能逐项覆盖 Gate 6 报告中的 P1 阻塞项。

### 阶段 R1：首页长期定位与信息架构修复

目标：让首页先表达长期产品身份，再表达 V1 首批项目。

核心交付物：

- 新首页首屏；
- 长期产品骨架区；
- V1 首批项目区；
- 复现路径区；
- 项目地图语义区；
- 反馈入口位置。

出口验收标准：

- 首屏必须出现“公开、公益、可复现的 vibe coding 项目地图”或同义表达；
- 首屏必须回答：这是什么长期产品、适合谁、现在先做什么；
- 首屏主文案不得把整个站点定义为“5 个纯 Web 小项目”；
- “5 个纯 Web 小项目”只能出现在 V1 首批项目区或首批项目说明中；
- 首页必须保留“从第一个项目开始”和“查看首批项目”两个行动入口；
- 首页必须展示复现路径，且路径中必须包含“看源码”；
- 首页必须让用户理解当前 5 个项目是 V1 / 首批 release，而不是长期边界；
- 不允许新增复杂搜索、筛选、投稿、账号、评论或排行。

### 阶段 R2：语言模型与中英文切换

目标：默认中文体验完整，同时提供英文切换能力。

核心交付物：

- locale 类型；
- 中英文 dictionary；
- 语言切换控件；
- 本地保存用户语言选择；
- `html lang` 动态同步；
- 页面级和 demo 级本地化策略。

出口验收标准：

- 首次打开页面默认中文；
- App shell 中有清晰语言切换入口；
- 切换英文后，导航、首页、至少一张项目卡、一个详情页和一个 demo 的主要文案立即变化；
- 用户选择的语言保存在 localStorage，刷新后保持；
- `document.documentElement.lang` 与当前语言一致；
- 中文模式下用户可见按钮、状态、表单标签、错误提示、文档入口标签默认中文；
- `Codex`、`GitHub`、文件路径、API 名称、品牌型英文项目代号可以保留英文，但必须有中文展示名或中文解释。

### 阶段 R3：项目元数据、详情页与文档入口本地化

目标：项目卡、详情页、文档入口在中文模式下不再大面积英文混杂。

核心交付物：

- 项目中文展示名；
- 项目英文展示名；
- 本地化项目摘要、路径角色、能力标签、难度、预计时间；
- 本地化详情页模板；
- 本地化文档入口标签。

出口验收标准：

- 5 张项目卡在中文模式下展示中文项目名或“中文名 + 英文代号”；
- 难度显示为“难度 1/2/3”或同等级中文表达，不显示 `Level 1`；
- 预计时间显示为中文时间表达，不显示 `45 minutes`；
- 项目详情页主要按钮中文模式下不显示 `Open Live Demo`；
- 文档标签中文模式下显示“Codex 从 0 到 1”“源码导览”“复杂度拆解”“常见问题”“二创任务”；
- 英文模式下这些字段切换为英文。

### 阶段 R4：五个 demo 用户可见文案本地化

目标：五个 demo 的核心体验在中文模式下可被中文小白理解。

核心交付物：

- Pomodoro demo 文案本地化；
- Memory Cards demo 文案本地化；
- Tiny Ledger demo 文案本地化；
- Habit Grid demo 文案本地化；
- Split Console demo 文案本地化；
- 语言相关格式化 helper。

出口验收标准：

- 中文模式下 Memory Cards 不再显示 `Moves`、`Restart game`、`Pick one more card.` 等英文 UI；
- 中文模式下 Pomodoro 不再显示 `Start`、`Pause`、`Reset`、`Completed Today` 等英文 UI；
- 中文模式下 Ledger 不再显示 `Income`、`Expense`、`Add record` 等英文 UI；
- 中文模式下 Habit Grid 不再显示主要英文 UI；
- 中文模式下 Split Console 不再显示 `Total`、`Participants`、`Copy summary` 等英文 UI；
- 用户可见金额、日期、数量文案跟随当前语言；
- 用于内部 key 的稳定日期格式可以保留实现细节，但不能作为用户可见文案暴露。

### 阶段 R5：真实源码入口

目标：源码入口从站内源码导览锚点升级为真实可访问源码位置。

核心交付物：

- 项目源码入口数据模型；
- 每个项目的源码文件清单；
- 静态源码树或公开源码包入口；
- 项目详情页“查看源码”链接；
- source-guide 对真实源码入口的解释。

出口验收标准：

- `links.source` 不得再指向 `#/projects/{slug}?section=source-guide`；
- 每个项目详情页必须有可点击的真实源码入口；
- 源码入口可以是 GitHub 仓库、GitHub 目录、GitHub 文件、公开源码包或静态源码树；
- 如果采用静态源码树，生产构建必须能访问对应源码文本或源码包；
- 每个项目源码入口必须能定位到该项目核心代码目录或核心文件清单；
- source-guide 可以继续存在，但只能作为导览，不能替代源码入口；
- E2E 必须验证 5 个项目源码入口不是 hash-only guide link，且目标可访问。

### 阶段 R6：中文优先复现文档

目标：默认文档从英文优先改为中文小白可执行。

核心交付物：

- 5 份中文优先 Codex 从 0 到 1 文档；
- 5 份中文优先源码导览；
- 5 份中文优先复杂度拆解；
- 5 份中文优先 FAQ；
- 5 份中文优先二创任务；
- 英文文档策略说明。

出口验收标准：

- 每个项目 `codex-from-zero.md` 标题和主体默认中文；
- 每个项目 `source-guide.md` 标题和主体默认中文；
- FAQ 至少 5 个问题，默认中文；
- remix prompts 至少轻改、中改、深改 3 类，默认中文；
- 文档可以保留英文专有名词，但不能以英文作为主要解释语言；
- 若英文文档暂不独立维护，必须在 release review 中明确英文模式下文档策略。

### 阶段 R7：反馈入口策略修复

目标：保留反馈入口位置，但不默认绑定 X 或任何未决外部平台。

核心交付物：

- 反馈入口状态模型；
- 首页反馈区；
- 项目详情页反馈入口；
- 反馈策略说明文档；
- release risk 更新。

出口验收标准：

- 首页仍能找到反馈入口位置；
- 项目详情页仍能找到反馈入口；
- 如果反馈渠道未最终确定，按钮不得直接跳转 X；
- 未决状态应显示“反馈方式准备中”或进入站内说明区；
- 文案仍引导四类信息：最感兴趣项目、是否愿意复现、卡住位置、二创想法；
- 不引入评论区、账号、社区、投稿或反馈数据库；
- E2E 必须验证不存在默认 `x.com/intent/post` 反馈链接。

### 阶段 R8：Gate 6 复验包

目标：用新验收口径重新证明 V1 是否可公开发布。

核心交付物：

- 新 release review；
- 新 acceptance rereview 报告；
- 更新后的 visual / accessibility / i18n QA 证据；
- 更新后的 README；
- 完整验证命令记录。

出口验收标准：

- `npm run test:run` 通过；
- `npm run build` 通过；
- `npm run test:e2e` 通过；
- `git diff --check` 通过；
- `git status --short --branch` 干净；
- E2E 覆盖默认中文、英文切换、源码入口、反馈未绑定 X、390/768/1440 响应式；
- 新 acceptance report 结论明确为通过或不通过，不能继续沿用旧 release review Pass。

## 6. 发布复验通过标准

V1 只有同时满足以下条件，才能重新建议公开发布：

- 首页第一屏表达长期产品身份，而不是把站点定义为 5 个项目；
- 当前 5 个项目被明确表达为 V1 首批项目；
- 整站信息架构体现项目地图、复现路径和可持续扩展语义；
- 每个项目都有真实源码入口；
- 默认中文体验完整；
- 英文切换可用；
- 五个 demo 动态状态文案已本地化；
- 项目文档默认中文优先；
- 反馈入口不默认跳 X，且未引入社区系统；
- 仍然没有后端、数据库、登录、支付、API、投稿、排行等 V1 非目标；
- 构建、测试、E2E 全绿；
- 发布前风险清单没有阻断项。

## 7. 明确不做

本轮 remediation 不做：

- 新增第 6 个项目；
- 上线登录或账号；
- 新建后端、数据库、云函数；
- 接入第三方 API 或 AI API；
- 接入支付；
- 做评论区、论坛、投稿、排行榜；
- 做复杂搜索或筛选；
- 做完整 V2 项目路径推荐；
- 做完整课程体系；
- 为 i18n 引入复杂 CMS；
- 为源码入口引入动态服务端。

## 8. 需要产品层继续确认的问题

以下问题不阻塞 remediation plan 编写，但会影响最终实现选择：

- 公开源码入口最终采用 GitHub 仓库、GitHub 目录、GitHub 文件、静态源码树还是源码包；
- 反馈入口最终采用邮箱、GitHub Issue、轻量表单、站内说明还是社交话题；
- 英文文档是独立维护，还是仅先明确英文模式下的文档策略；
- V1 复验报告文件名是否采用 `2026-06-13-v1-gate6-release-rereview-acceptance-report.md`。
