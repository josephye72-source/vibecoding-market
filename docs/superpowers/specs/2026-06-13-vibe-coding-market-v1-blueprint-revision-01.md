# Vibe Coding Market V1 蓝图修订版 01

日期：2026-06-13
状态：生效，作为后续执行与复验的 V1 产品蓝图基线
关联验收报告：`docs/reviews/acceptance/2026-06-13-v1-gate6-release-acceptance-report.md`

## 1. 文档定位

这份文档是 Vibe Coding Market V1 的蓝图修订版。

它不是代码实现计划，也不是单个页面设计稿。它定义的是 V1 应该作为一个产品被用户如何理解、如何使用、如何验收。

后续首页、整站信息架构、项目详情页、源码入口、反馈入口、语言系统和发布验收，都应以本蓝图修订版为产品层基线。

如果本文与旧 V1 基准 Spec 存在冲突，以本文为准。旧 V1 基准 Spec 仍然可以作为执行细节参考，但不再单独决定产品表达。

文档优先级：

1. 大蓝图与北极星；
2. 本 V1 蓝图修订版；
3. V1 蓝图；
4. V1 基准 Spec；
5. 具体执行计划；
6. 当前实现细节。

## 2. 产品背景

Vibe Coding Market 是一个公开、公益、可复现的 vibe coding 项目地图。

它要帮助普通人理解：AI 不只是聊天工具，也可以陪人把想法做成可运行的软件。

站点长期要沉淀的是一套公开实践方法：

想法 -> 项目选择 -> 在线体验 -> 复杂度拆解 -> Codex 复现 -> 源码阅读 -> 二创发布。

V1 是这个长期产品的第一版路径验证，不是最终形态，也不是完整项目库。

## 3. 北极星

Vibe Coding Market 的北极星是：

一个完全编程小白能不能通过这里的项目，用 Codex 做出自己的第一个可发布 Web 作品。

所有 V1 产品判断都应该围绕这件事：

- 用户是否能快速理解站点是什么；
- 用户是否愿意点开一个项目；
- 项目是否足够好看、好玩、有用；
- 文档是否能让小白复现；
- 源码是否能被看懂；
- 用户是否有动力二创并公开分享。

如果一个功能不能增强“体验 -> 复现 -> 二创”这条路径，就不应该进入 V1。

## 4. V1 产品目标

V1 的目标不是“做一个只有 5 个项目的网站”。

V1 的目标是：

用 5 个高完成度纯 Web 项目验证 Vibe Coding Market 这条路径是否成立。

V1 需要证明：

- 这种项目地图形态能让小白愿意开始；
- 在线 demo 能让用户理解最终效果；
- 源码和文档能支撑用户复现；
- Codex 操作文档对小白足够可执行；
- 用户能产生二创和反馈意愿；
- 这套模板能支撑后续 2.0 的项目扩展。

## 5. 产品边界

### V1 必须做

- 一个能表达长期产品定位的首页；
- 一个清晰的新手路径表达；
- 5 个首发纯 Web 项目；
- 5 个在线 demo；
- 5 个项目详情页；
- 每个项目一个真实源码入口；
- 每个项目一套 Codex 从 0 到 1 复现文档；
- 每个项目一套复杂度拆解；
- 每个项目一套源码导览；
- 每个项目一套常见问题；
- 每个项目一套二创任务；
- 一个反馈入口位置；
- 中文默认体验；
- 英文切换能力。

### V1 不做

- 登录；
- 账号系统；
- 用户中心；
- 后端服务；
- 数据库；
- 云函数；
- 第三方 API；
- AI API；
- 付费；
- 会员；
- 商业转化漏斗；
- 项目投稿平台；
- 评论区；
- 论坛；
- 社区；
- 排行榜；
- 复杂搜索；
- 复杂筛选；
- 完整多路径推荐；
- 完整课程体系；
- 重型 WebGL 或复杂 3D；
- 需要复杂素材管理、拖拽工作流、文件上传、音频同步或复杂导出的项目。

## 6. 目标用户

V1 第一优先用户是中文语境下的编程小白。

他们可能：

- 没有系统学过前端；
- 不了解工程化；
- 听说过 AI / Codex，但不知道如何从一个想法做成作品；
- 希望先看到一个好看、可玩的成品，再决定要不要跟做；
- 需要可复制的 Prompt、清晰步骤和失败处理。

第二优先用户是有一点前端基础的人。

他们可以从项目结构、源码导览、Prompt 组织和二创任务里获得练习价值，但 V1 不应假设他们已经懂完整前端体系。

## 7. 产品定位

Vibe Coding Market 应该像一个高完成度、可持续扩展的公开项目地图。

它不是：

- 课程销售页；
- 训练营入口；
- 普通教程博客；
- 白底卡片式 demo 集合；
- AI 工具导航；
- SaaS 产品；
- 项目外包市场；
- 重社区平台；
- 低质量 demo 列表。

V1 页面可以展示 5 个首发项目，但不能让用户以为整个站点的长期定义就是“5 个小游戏 / 5 个小工具”。

## 8. 信息架构

V1 首页需要同时承担两件事：

1. 说明长期产品是什么；
2. 展示当前 V1 首批项目。

推荐首页结构：

1. 长期产品首屏
   - 说明 Vibe Coding Market 是公开、公益、可复现的 vibe coding 项目地图；
   - 说明它适合想用 Codex 做出真实 Web 作品的人；
   - 保留“从第一个项目开始”的行动入口；
   - 不把主文案写成“5 个项目”。

2. 当前 V1 首批项目
   - 明确这是 V1 / 首批 release；
   - 展示 5 个纯 Web 项目；
   - 每个项目可以在线体验、看源码、跟 Codex 做。

3. 复现路径
   - 先玩；
   - 看懂；
   - 看源码；
   - 跟做；
   - 二创。

4. 项目地图语义
   - 轻量说明后续会有更多项目和路径；
   - 不做复杂筛选或搜索；
   - 不让用户误以为 V1 已经是完整项目库。

5. 反馈入口
   - 可以保留按钮和区域；
   - 当前反馈渠道未定时，不应直接跳转 X；
   - 可以显示“反馈方式准备中”或进入站内说明。

## 9. 首页要求

首页第一屏必须回答：

1. 这是什么长期产品？
2. 适合谁？
3. 我现在可以先做什么？

首页第一屏推荐表达：

- Vibe Coding Market 是一个公开、公益、可复现的 vibe coding 项目地图；
- 这里的项目都能在线体验、阅读源码、跟 Codex 从 0 到 1 复现；
- V1 首批提供 5 个纯 Web 项目，用来验证这条路径。

首页第一屏不应把主文案写成：

- `5 个纯 Web 小项目，带你用 Codex 从 0 做到可发布`

这句话可以作为首批项目区的说明，而不是整站定义。

首页必须保留：

- 进入第一个项目的主行动入口；
- 查看首批项目的次行动入口；
- 公益、开源、无需登录、无后端、可复现等定位标签；
- 新手路径；
- 当前首批项目；
- 反馈入口位置。

## 10. V1 首发项目

V1 首发项目仍然是：

1. 专注番茄钟；
2. 记忆翻牌小游戏；
3. 极简记账本；
4. 习惯打卡日历；
5. 预算 / 分摊计算器。

这些项目的角色是验证路径，而不是定义整个站点的长期边界。

项目区应使用类似“V1 首批项目”“当前首发项目”“从这 5 个项目开始”这样的表达。

## 11. 项目详情页要求

每个项目详情页必须包含：

1. 项目头部；
2. 在线体验；
3. 你会学到什么；
4. 复杂度从哪里来；
5. 源码入口与源码导览；
6. Codex 从 0 到 1 文档；
7. Prompt 区；
8. 常见问题；
9. 二创任务。

项目详情页的目标不是教学理论，而是帮助用户完成：

体验成品 -> 看懂结构 -> 找到源码 -> 跟 Codex 复现 -> 做二创。

## 12. 源码入口要求

V1 的“源码开放”不能只停留在源码导览。

每个项目至少要提供一种真实源码入口：

- GitHub 仓库；
- GitHub 目录链接；
- GitHub 文件链接；
- 公开源码包；
- 或其他明确可访问的源码位置。

源码导览可以保留，但不能替代源码入口。

如果某个项目共用同一个仓库，也需要能从项目详情页直接定位到该项目代码目录。

## 13. Codex 文档要求

每个项目必须有一份面向小白的 Codex 从 0 到 1 复现文档。

文档必须包含：

- 项目目标；
- 准备条件；
- 从空文件夹开始；
- 第一次 Prompt；
- Codex 应产出的文件；
- 如何运行或打开；
- 验收清单；
- 分步改进 Prompt；
- 常见失败处理；
- 二创 Prompt。

文档默认语言应为中文，并支持英文版或英文切换策略。

## 14. 语言要求

V1 默认主语言是中文。

V1 必须支持切换到英文版。

中文模式下：

- 导航、首页、项目卡、详情页、demo、状态反馈、按钮、文档入口都应是中文；
- 项目英文名可以保留，但必须有中文展示名或中文解释；
- `Codex`、`GitHub`、文件路径、API 名称等专有名词可以保留英文。

英文模式下：

- 至少导航、首页、项目卡、详情页、demo 主要文案应切换为英文；
- 文档策略需要明确：是维护独立英文文档，还是通过本地化内容生成。

## 15. 反馈入口要求

V1 可以保留反馈入口位置，但当前不应直接绑定 X。

原因：

- 当前 V1 仍是 release candidate；
- 反馈渠道还没有产品层最终决策；
- 直接跳 X 会让站点显得已经进入外部推广阶段；
- X 不应被默认视为唯一正式反馈渠道。

可选反馈方式：

- 邮箱；
- 站内信；
- GitHub Issue；
- 轻量表单；
- 社交话题。

如果反馈渠道暂未确定，按钮可以保留，但功能可以是：

- 占位；
- 打开站内说明；
- 显示“反馈方式准备中”；
- 或引导用户等待公开反馈入口。

## 16. 视觉与交互要求

V1 继续采用 Studio Anthology 策略：

- 站点外壳统一、清楚；
- 项目 demo 各有视觉人格；
- 项目不是同一套模板换色；
- 视觉服务项目理解和交互反馈；
- 不使用难以复现的重型 3D / WebGL / 复杂素材系统。

整站视觉应服务长期产品，而不只是包装 5 个当前项目。

## 17. V1 成功标准

V1 成功不是项目数量多，而是路径成立。

V1 成功标准：

- 用户在首页第一屏理解 Vibe Coding Market 是什么；
- 用户知道当前 V1 有 5 个首批项目，而不是以为站点永远只有 5 个项目；
- 用户愿意点开至少一个项目；
- 每个项目都能在线体验；
- 每个项目都有真实源码入口；
- 每个项目都有 Codex 复现文档；
- 默认中文体验成立；
- 英文切换能力存在；
- 至少一个小白能跟文档复现出 70% 以上效果；
- 反馈能帮助判断哪个项目最吸引人、用户在哪一步卡住、是否愿意二创。

## 18. 发布验收标准

V1 只有同时满足以下条件，才能建议公开发布：

- 首页长期定位准确；
- 当前 5 个项目被表达为 V1 首批项目；
- 整站信息架构体现长期项目地图和复现系统；
- 不提前实现 V2/V3 复杂功能；
- 5 个 demo 均可体验；
- 5 个项目均有真实源码入口；
- 5 个项目均有中文优先 Codex 文档；
- 默认中文体验完整；
- 英文切换可用；
- 反馈入口策略清楚，且不默认跳 X；
- 无后端、数据库、登录、支付、API、社区、投稿、排行等 V1 非目标；
- 构建、测试、E2E 通过；
- 发布前风险清单没有阻断项。

## 19. V2 进入条件

V1 发布后不能自动进入 V2。

只有在真实反馈证明路径成立后，才讨论 V2。

进入 V2 的必要信号：

- 至少有人尝试复现，或明确表达复现意愿；
- 至少一个小白能复现出 70% 以上效果；
- 能看出哪个项目最吸引人；
- 能看出文档或源码哪里卡住用户；
- 能判断下一批项目应扩展哪类方向。

如果没有复现信号，先修 V1，不进入 V2。

## 20. 未决问题

以下问题需要后续产品层继续决策：

- 英文版文档是独立维护，还是由本地化内容生成；
- 反馈入口最终使用邮箱、站内信、GitHub Issue、轻量表单还是社交话题；
- 源码入口采用单一总仓库目录，还是每个项目一个独立仓库；
- V1 发布时是否需要一个“项目地图未来方向”模块；
- V1 首屏文案最终版本。
