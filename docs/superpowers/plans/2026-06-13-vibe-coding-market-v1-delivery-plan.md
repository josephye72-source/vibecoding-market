# Vibe Coding Market 1.0 项目交付规划

> 状态更新，2026-06-13：本文件是第一轮 V1 交付规划。Gate 6 发布验收不通过后，V1 的下一轮项目管理基线应以 `docs/superpowers/specs/2026-06-13-vibe-coding-market-v1-blueprint-revision-01.md`、`docs/superpowers/specs/2026-06-13-vibe-coding-market-v1-gate6-remediation-spec.md` 和 `docs/superpowers/plans/2026-06-13-vibe-coding-market-v1-gate6-remediation-plan.md` 为准。

日期：2026-06-13
状态：项目规划草案，等待用户确认

## 1. 规划结论

Vibe Coding Market 1.0 的项目目标不是做一个“大而全”的项目站，而是做出一个可被战略层验收的路径验证版。

1.0 必须证明一件事：一个完全编程小白，是否能通过少量高完成度的纯 Web 项目，完成“先体验 -> 看懂 -> 用 Codex 复现 -> 二创”的闭环。

因此，第一版的项目管理原则是：

- 少项目，高闭环；
- 先验证一个完整项目，再复制到五个项目；
- 站点外壳统一，项目 demo 各有视觉人格；
- 所有项目坚持纯 Web，拒绝后端、账号、数据库、第三方 API；
- 文档必须可执行，不写成概念教程；
- 所有阶段都围绕战略 Review Gates 推进。

本规划基于三份顶层文件：

- `docs/superpowers/specs/2026-06-13-vibe-coding-market-strategy-session-charter.md`

这三份文件已经给出足够清楚的战略边界：1.0 是路径验证版，2.0 是路径扩展版，3.0 是开放生态版。当前规划只服务 1.0，不提前引入 2.0 / 3.0 的复杂度。

## 3. 1.0 战略验收口径

1.0 通过战略层验收，至少要满足：

- 首页第一屏能让小白理解这是什么、适合谁、下一步点哪里；
- 5 个项目都是纯 Web 项目；
- 5 个项目都能在线体验；
- 5 个项目都有源码入口；
- 5 个项目都有 Codex 从 0 到 1 复现文档；
- 每个项目都有统一详情页结构、复杂度拆解、学习点和二创方向；
- 至少一个项目是游戏；
- 站点不像课程销售页、训练营入口、SaaS 工具或普通 demo 列表；
- 项目整体适合公开发布并收集反馈；
- 发布后能判断哪个项目最吸引人、用户在哪一步卡住、文档模板是否有效。

## 4. 1.0 交付物清单

### 4.1 站点层交付物

- 首页；
- 新手路径模块；
- 5 个项目卡片；
- 统一项目详情页模板；
- 反馈或社交分享入口；
- 站点级视觉外壳；
- 项目元数据模板。

### 4.2 项目层交付物

每个项目必须交付：

- 在线 demo；
- 源码入口；
- 项目详情页；
- 复杂度拆解；
- 源码导览；
- Codex 从 0 到 1 操作文档；
- 常见问题；
- 至少 3 个二创任务；
- 可用于首页卡片的项目元数据。

### 4.3 1.0 首发项目

| 顺序 | 项目 | 路径角色 | 验收重点 |
| --- | --- | --- | --- |
| 1 | 专注番茄钟 | 第一个实用小应用 | 用它验证第一条完整闭环 |
| 2 | 记忆翻牌小游戏 | 第一个游戏项目 | 确认至少一个游戏项目成立 |
| 3 | 极简记账本 | 本地数据工具 | 验证表单、列表、统计、localStorage |
| 4 | 习惯打卡日历 | 进度反馈工具 | 验证日期、日历网格、连续反馈 |
| 5 | 预算 / 分摊计算器 | 场景型实用工具 | 验证多项输入、自动计算、结果摘要 |

## 5. 推荐执行策略

不要同时推进 5 个项目。推荐采用“一号项目闭环验证 -> 模板固化 -> 批量复制”的方式。

### 阶段 0：战略范围冻结

目标：确认 1.0 不再扩范围。

主要任务：

- 确认 5 个首发项目不变；
- 确认 1.0 不做登录、后端、数据库、AI API、投稿、评论、排行榜；
- 确认第一个完整原型从“专注番茄钟”开始；
- 确认反馈入口形式。

输出物：

- V1 项目清单确认；
- V1 非目标清单确认；
- 第一原型项目确认；
- 战略 Gate 1 评审记录。

对应战略验收：

- Gate 1：项目清单 Review。

### 阶段 1：首页与信息架构

目标：让用户第一眼理解站点，并知道先点哪个项目。

主要任务：

- 设计首页结构；
- 定义项目卡信息；
- 定义新手路径表达；
- 定义项目详情页统一结构；
- 定义项目元数据字段；
- 确认反馈入口在页面中的位置。

输出物：

- 首页信息架构；
- 项目详情页结构；
- 项目卡字段；
- 项目元数据模板。

对应战略验收：

- Gate 2：首页与信息架构 Review。

### 阶段 2：视觉策略落地

目标：确认 Studio Anthology 策略可以执行。

主要任务：

- 定义站点外壳视觉原则；
- 定义 5 个项目 demo 的视觉母题；
- 明确哪些视觉手法允许，哪些不允许；
- 建立项目 demo 的视觉完成度底线；
- 避免所有项目变成同一套模板换色。

输出物：

- 站点外壳视觉方向；
- 5 个项目视觉母题说明；
- 视觉风险清单；
- 可供执行 session 使用的视觉约束。

对应战略验收：

- Gate 3：视觉策略 Review。

### 阶段 3：第一个项目闭环原型

目标：用“专注番茄钟”验证完整方法，而不是只验证一个 demo。

主要任务：

- 完成专注番茄钟在线 demo；
- 完成专注番茄钟详情页；
- 完成源码结构与源码导览；
- 完成 Codex 从 0 到 1 操作文档；
- 完成常见失败处理；
- 完成二创任务；
- 做一次小白视角 walkthrough。

输出物：

- 第一个可在线体验项目；
- 第一个项目详情页；
- 第一份 Codex 复现文档；
- 第一版复杂度拆解；
- 第一版二创任务。

对应战略验收：

- Gate 4：第一个项目原型 Review；
- Gate 5：Codex 文档 Review 的首轮样本。

### 阶段 4：模板固化

目标：把第一个项目沉淀成可复制模板。

主要任务：

- 固化项目详情页模板；
- 固化 Codex 文档模板；
- 固化项目元数据模板；
- 明确 demo、源码、文档、详情页之间的链接规则；
- 明确每个项目的 Definition of Done。

输出物：

- 项目详情页模板；
- Codex 文档模板；
- 项目元数据模板；
- 单项目验收清单。

对应战略验收：

- Gate 5：Codex 文档 Review。

### 阶段 5：剩余四个项目批量执行

目标：在不稀释质量的前提下完成剩余 4 个项目。

推荐顺序：

1. 记忆翻牌小游戏；
2. 极简记账本；
3. 习惯打卡日历；
4. 预算 / 分摊计算器。

主要任务：

- 每个项目按模板完成 demo、详情页、源码导览、Codex 文档、FAQ、二创任务；
- 每完成一个项目做一次轻量战略检查；
- 避免每个项目自行发明一套页面结构；
- 只允许 demo 层视觉个性化，不允许学习结构混乱。

输出物：

- 5 个完整项目；
- 5 套源码入口；
- 5 份 Codex 文档；
- 5 个项目详情页；
- 完整首页项目区。

对应战略验收：

- Gate 6：1.0 Release Review 的前置条件。

### 阶段 6：发布前战略验收

目标：判断 1.0 是否可以公开发布。

主要任务：

- 按 Gate 1-6 做整体验收；
- 检查是否出现范围膨胀；
- 检查所有 demo 是否可体验；
- 检查所有源码和文档入口是否完整；
- 检查首页是否像项目地图，而不是课程销售页；
- 检查是否能收集有效反馈。

输出物：

- 1.0 Release Review 记录；
- 发布风险清单；
- 发布后反馈收集方案。

对应战略验收：

- Gate 6：1.0 Release Review。

### 阶段 7：发布后反馈 Review

目标：判断是否进入 2.0。

主要任务：

- 收集用户点击、评论、复现尝试、二创意愿；
- 判断哪个项目最吸引人；
- 判断哪个文档步骤最容易卡住；
- 判断是否有人能复现 70% 以上效果；
- 判断 2.0 应优先扩展哪类项目。

输出物：

- 1.0 Feedback Review；
- 是否进入 2.0 的建议；
- 2.0 优先项目类型建议；
- 文档模板修正建议。

对应战略验收：

- Gate 7：1.0 Feedback Review。

## 6. 单项目 Definition of Done

一个项目只有同时满足以下条件，才算 1.0 可交付：

- demo 可直接打开并完成核心体验；
- demo 不依赖后端、登录、数据库或第三方 API；
- 项目视觉有明确母题，不是普通模板换色；
- 功能边界清楚，没有额外膨胀；
- 有源码入口；
- 有源码导览，告诉小白优先看哪些文件；
- 有复杂度拆解；
- 有 Codex 从 0 到 1 操作文档；
- 文档从空文件夹开始；
- 文档每一步都有 Prompt、预期产出、验收方式；
- 文档包含常见失败处理；
- 有轻改、中改、深改三个层级的二创任务；
- 能被首页和详情页用统一元数据呈现。

## 7. 工作流与 Review 机制

建议把后续执行拆成多个执行 session，每个 session 回到战略层时必须带：

- 本次目标；
- 对应版本与 Review Gate；
- 产出文件或链接；
- 已完成内容；
- 未完成内容；
- 风险点；
- 需要战略层决策的问题。

推荐执行 session：

1. 首页与信息架构 session；
2. 视觉策略 session；
3. 专注番茄钟 demo session；
4. 专注番茄钟 Codex 文档 session；
5. 项目详情页模板 session；
6. 记忆翻牌小游戏 session；
7. 极简记账本 session；
8. 习惯打卡日历 session；
9. 预算 / 分摊计算器 session；
10. 1.0 发布验收 session。

## 8. 风险与控制策略

| 风险 | 表现 | 控制方式 |
| --- | --- | --- |
| 范围膨胀 | 想加登录、投稿、评论、排行榜、搜索 | 一律推迟到 2.0 / 3.0，1.0 只保留反馈入口 |
| 视觉过度复杂 | 项目很酷但小白无法复现 | 视觉必须能用 CSS、布局、轻量动效解释 |
| 文档变成教程文章 | 讲太多概念，不能直接执行 | 每一步必须有 Prompt、产出、验收 |
| 五个项目质量不均 | 有的项目像半成品 | 先完成第一个闭环，再复制模板 |
| 项目隐藏复杂度过高 | 日期、存储、计算、响应式让小白卡住 | 每个项目必须提前做复杂度拆解 |
| 站点定位跑偏 | 看起来像课程销售页或 SaaS | 首页文案优先项目体验和可复现，不做转化漏斗 |
| 发布后反馈无效 | 只有浏览，没有复现信号 | 反馈入口要主动询问体验、复现、卡点和二创 |

## 9. 1.0 项目管理节奏

如果以单主线推进，建议按以下节奏：

- 第 1 批：范围冻结、首页信息架构、视觉策略；
- 第 2 批：专注番茄钟完整闭环；
- 第 3 批：模板固化；
- 第 4 批：剩余四个项目；
- 第 5 批：发布前验收和反馈机制。

如果有多个执行 session 并行，最多只建议并行三类工作：

- 首页 / 信息架构；
- 视觉策略；
- 第一个项目原型。

在第一个项目原型通过 Gate 4 之前，不建议全面并行开发剩余 4 个项目。

## 10. 当前需要用户确认的决策

为了让执行进入下一步，需要确认：

1. 1.0 的 5 个首发项目是否锁定为：专注番茄钟、记忆翻牌小游戏、极简记账本、习惯打卡日历、预算 / 分摊计算器。
2. 第一个完整原型是否锁定为“专注番茄钟”。
3. 1.0 是否坚持静态纯 Web 优先，只有收益明显时才允许 Node / Vite。
4. 反馈入口采用什么形式：GitHub issue、社交媒体话题、表单链接，还是先用最轻量的联系方式。
5. 是否把“至少一个小白能复现 70% 以上效果”作为 1.0 发布后的核心验证指标。

## 11. 下一步建议

下一步不应该直接开做 5 个项目。建议先启动三个执行动作：

1. 做 Gate 1 项目清单确认；
2. 开首页与信息架构执行 session；
3. 开专注番茄钟完整闭环执行 session。

只要第一个项目闭环通过战略 Review，后续 4 个项目就可以进入模板化复制阶段。
